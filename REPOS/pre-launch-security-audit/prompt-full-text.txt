01 Secrets and API keys
A leaked key is a blank cheque. Bots constantly scan public code and app bundles for keys.
1.1 No secret keys in frontend or app code
Anything that ships to users (React code, built files, Expo app bundles) can be extracted. Search for: EMERGENT_LLM_KEY
or anything starting sk-emergent-, OpenAI/Anthropic/Gemini keys, Stripe sk_ keys, MongoDB connection strings
(mongodb+srv://), JWT secrets, Supabase service_role keys. Check env variables with public prefixes (REACT_APP_,
NEXT_PUBLIC_, EXPO_PUBLIC_, VITE_): they ship to every user. Pass: only publishable keys are client-side.
1.2 No secrets committed to code or Git history
.env files are git-ignored before saving to GitHub. No secrets in config files or history. If one was ever committed,
deleting it isn't enough: it must be revoked and replaced.
1.3 Secrets are stored properly
All secrets come from Emergent Secrets (Preview →  Manage →  Secrets) or environment variables, never hardcoded.
Preview and live use different keys where possible.
1.4 No secrets in logs, errors or analytics
Keys, tokens and passwords are never logged, returned in error messages or sent to analytics tools.
02 Login and sessions
Every other protection assumes we know who the user is.
2.1 Every private route verifies the session on the server
Each FastAPI route and server action that touches private data checks the session or token on the server, including
Emergent Auth sessions. Hiding a button in the UI is not protection. List every private route in AUDIT.md.
2.2 Passwords are handled safely
Prefer Emergent Auth or another managed provider. If the app stores passwords itself, they're hashed with bcrypt or
argon2, never plain text or reversible encryption. No admin or test account is created at startup with a password written
in the code or a default password. If one exists, mark it Critical.
2.3 Password reset and email verification are safe
Reset links expire, work once and can't be guessed. Responses don't reveal whether an email is registered.
2.4 Login is protected from guessing
Rate limits or lockouts on login, signup, OTP and password reset (see 6.1 for how).

2.5 Tokens are verified and expire
Tokens are verified with their signature (never just decoded), the none algorithm is rejected, no default or example
secret is used, sessions expire and logout ends them. Session cookies are HttpOnly, Secure and SameSite.
2.6 Tokens aren't kept in localStorage
If the login method supports secure cookies, tokens shouldn't sit in localStorage or sessionStorage, where any
injected script can read them. If they do, flag it as Medium. Report only: never move token storage as a fix.
2.7 Social login redirects are locked down
Google sign-in and other OAuth redirect URLs are an exact allowlist, and there's no open redirect after login.
03 Access control
Broken access control is the number 1 risk in the OWASP Top 10 (2025). The classic version: logged in as Rahul, change an ID in
the URL, see Priya's data.
3.1 Every record checks ownership
Every read, update and delete filters by the logged-in user (or their team), for example
{"_id": id, "user_id": current_user.id}, not just by ID. List every collection and route checked in AUDIT.md.
3.2 Users can't promote themselves
Create and update endpoints, including signup, use separate Pydantic models that exclude role, is_admin, plan,
credits, balance, verified and subscription_status. The request body is never written straight into the
database.
3.3 Admin areas are protected on the server
Admin pages and APIs check an admin role on the server. A secret URL is not protection.
3.4 Paid features and limits are enforced on the server
Plan limits, credits, usage caps and premium features are checked server-side, not only hidden in the UI.
3.5 Teams stay separate
If the app has teams or workspaces, every query is scoped to the user's own team.
3.6 Debug and test routes are off in production
No public debug pages, test endpoints, seed scripts or "temporary" admin routes.
04 Database and file storage
Your database holds everything users trust you with. Most leaks come from a missing rule, not a clever hack.
4.1 Database queries can't be hijacked
User input never goes straight into a MongoDB query. For example, a login request sending {"$ne": null} as the
password must not match every user. Validate types with Pydantic (strings stay strings), never pass raw request JSON as
a filter, and don't use $where or server-side JavaScript. If the app uses SQL anywhere, queries are parameterised.
4.2 Public IDs are random
IDs shown to users in URLs and API responses are random UUIDs, not MongoDB ObjectIds, which contain a timestamp
and counter and are partly predictable. Severity Low if 3.1 passes, because ownership checks are the real protection.
4.3 File storage is private by default
User files are private, served through short-lived signed URLs, and users can't overwrite each other's files.
4.4 The database isn't directly reachable
The MongoDB connection string is server-only, and network access isn't open to the whole internet where the user
controls it. Mark CAN'T VERIFY if it's managed by Emergent.

4.5 Only if you use Supabase or Firebase
In September 2026, UpGuard found 16,326 Supabase databases whose tables anyone could read because access rules
were missing. Supabase: RLS is on for every table, every policy checks auth.uid(), tables are granted only to the roles
that need them (never fix error 42501 by granting everything to anon), the service_role key is server-only, and
views or functions don't bypass RLS. Firebase: Firestore, Realtime Database and Storage rules aren't in test mode
(allow read, write: if true).
05 Input and output handling
Anything a user types, uploads or links to can be a weapon if the app trusts it blindly.
5.1 All input is validated on the server
Every FastAPI route uses Pydantic models with types, lengths and allowed values. Front-end validation alone doesn't
count.
5.2 No cross-site scripting (XSS)
User content is never inserted as raw HTML (dangerouslySetInnerHTML, innerHTML). Markdown and rich text are
sanitised.
5.3 File uploads are restricted
Type and size limits on the server, the real file type is checked, files are renamed, stored privately and never executed.
SVG and HTML uploads are blocked or sanitised.
5.4 No server-side request forgery (SSRF)
If the app fetches a URL a user provides, it allows only http(s), rejects any resolved address that isn't publicly routable,
and connects to the address it checked. Re-check after every redirect, and limit response size and time.
5.5 No open redirects
Any ?redirect= or ?next= parameter only allows the app's own paths.
5.6 Errors fail safely
Users see generic messages, never stack traces, database errors or file paths. If a multi-step action fails halfway
(payment taken but order not saved), the app rolls back or recovers.
06 API abuse protection
Bots don't need to hack you to hurt you. Spam, scraping and free-tier abuse drain money and data.
6.1 Rate limits that actually work
Per user and per IP limits on login, signup, OTP, password reset, forms, search, AI calls and uploads. Limits use shared
storage (for example the database or Redis), not in-memory counters that reset on restart or differ between servers,
and read the real client IP from the trusted proxy header, not the proxy's own IP. Never trust the first value of
X-Forwarded-For, because the client controls it. Use the address set by the platform's own proxy; if you can't confirm
how the proxy sets it, mark the IP source as Suspected. Limits on login and AI calls must also apply per account.
6.2 CORS allows only your domains
The real bug is accepting any origin while also allowing credentials. In FastAPI, allow_origins=["*"] with
allow_credentials=True does this. Require an exact list of your own origins.
6.3 Bot protection on public forms
Signup, contact and waitlist forms have a CAPTCHA (for example Cloudflare Turnstile) or similar.
6.4 APIs return only what's needed
Responses use Pydantic response models. They never include password hashes, tokens, internal fields or other users'
emails, and lists are paginated with a maximum page size.
6.5 CSRF protection
If login uses cookies, state-changing requests are protected (SameSite cookies plus CSRF tokens or origin checks).

6.6 Incoming webhooks are verified
Every Stripe, Razorpay (or other) webhook verifies the provider's signature, rejects failures and processes each event
only once.
07 Payments and money
Payment bugs turn directly into lost money, chargebacks and legal trouble.
7.1 Prices are decided on the server
The app sends only a plan or product ID. The server looks up the real price and never trusts an amount, currency or user
ID from the client.
7.2 Access is granted only after verified payment
Premium access comes from a verified Stripe or Razorpay webhook, or a server-side check of Razorpay's payment
signature, never from landing on a "success" page. Also a PASS: the server asks Stripe directly for the session's payment
status, provided the session belongs to the logged-in user and is credited only once. Don't rewrite a working flow like
this, but renewals and refunds (7.3) still need webhooks. Mobile in-app purchases are verified with Apple or Google on
the server.
7.3 The full payment lifecycle is handled
Renewals, failed payments, refunds, cancellations, downgrades and disputes all update access correctly.
7.4 Test and live keys are separated
Live secret keys are only on the server, in production.
7.5 Credits, coupons and trials can't be farmed
One trial per user, coupons checked server-side, and credit balances changed in a single atomic database update so
two fast requests can't spend the same credits twice.
7.6 Billing terms are visible
Price, billing period, auto-renewal and how to cancel are shown next to the pay button, and a working cancel option
exists.
08 AI features
Based on the OWASP Top 10 for LLM Applications. AI calls cost real money and can be manipulated.
8.1 AI usage has limits
Per-user quotas, rate limits, maximum input size, maximum output tokens and timeouts exist in the app. The Universal
LLM Key draws from your Emergent credit balance, so without per-user limits one user can burn your credits. At the
provider, use a hard spending cap where one exists; otherwise use prepaid credit with auto-recharge off.
8.2 The AI can't be talked into misusing its powers
Treat everything the model reads that the user didn't write (web pages, uploaded files, emails, other users' content) as
untrusted: hidden instructions in it must not trigger actions or reveal data. Tools the model can call are limited, scoped to
the current user's data, and require confirmation for anything destructive or costly. The model never gets unrestricted
database access.
8.3 AI output is treated as untrusted
Model output is escaped before display and never executed as code, database queries or shell commands.
8.4 No secrets in prompts
System prompts contain no keys, internal URLs or private data, and assume users may extract them.
8.5 AI memory is per-user
Chat history, vector stores and any RAG index are isolated per user or team.

09 Dependencies and supply chain
Software supply chain failures are number 3 in the OWASP Top 10 (2025).
9.1 No known vulnerable versions
Run pip-audit and npm audit (or yarn audit) and report Critical and High issues, focusing on packages that ship
to users or run on the server. Never run npm audit fix --force or any forced major upgrade; propose upgrades one
at a time in the fix round.
9.2 Versions are locked
requirements.txt pins versions and the frontend lockfile is committed. Avoid installing releases published in the last
few days.
9.3 Borrowed code has no hidden instructions
Scan imported templates, repos and packages for AI agent instruction files (such as AGENTS.md or other rules files),
hidden text in READMEs, and postinstall or other install scripts. Flag anything telling an AI to access secrets, run
commands or send data elsewhere.
9.4 Third-party scripts are minimal
Every external script (analytics, chat widgets, ads) is needed and loaded from its official source.
10 Deployment and configuration
Security misconfiguration is number 2 in the OWASP Top 10 (2025). One wrong setting can undo everything else.
10.1 Security headers are set
Report only. Read the headers from the page response, not only from /api responses, and report which are missing:
X-Content-Type-Options: nosniff, clickjacking protection (frame-ancestors or X-Frame-Options),
Referrer-Policy, Permissions-Policy and Content-Security-Policy. Don't add headers as a fix. If the user adds CSP
later, it should start in report-only mode, because a strict CSP can block the app's own scripts.
10.2 Production is in production mode
Debug mode and verbose logging are off. Decide deliberately whether source maps are public.
10.3 FastAPI docs are off or protected
/docs, /redoc and /openapi.json are disabled in production or require admin login, so they don't hand attackers a
map of every endpoint.
10.4 Sensitive files aren't served
/.env, /.git, backups, config files and database dumps aren't reachable, and directory listing is off.
10.5 Important events are logged
Failed logins, admin actions, permission changes and payment events are logged without passwords, tokens or full
personal data.
11 Cost and code health
Not security holes, but they drain batteries, slow apps and inflate bills, and AI-built apps hit them constantly.
11.1 No wasteful polling
Find code that calls the server every few seconds (setInterval, repeated fetches). The fix is to pause polling when the
screen is hidden and clean up when a screen closes. Suggest push updates (websockets, server-sent events) only as a
note.
11.2 No runaway costs
No infinite loops, functions that call themselves, retries without backoff, or scheduled jobs without limits, especially
anything that calls the AI key or paid APIs.

11.3 No duplicate or fallback versions
List v1/v2 copies, "backup" functions and dead code, with which one is actually used. Remove the rest only after the user
confirms (see the fix rules for live mobile apps).
12 Privacy and legal
An app can be fined or taken down before it makes its first sale. Not legal advice.
12.1 Privacy policy and terms are linked
Linked at signup and in the footer, stating what's collected, why, who it's shared with (including AI and analytics
providers), how long it's kept and how to get in touch.
12.2 Tracking waits for consent where required
For EU and similar users, analytics, ad pixels and session recording load only after consent, and session recording masks
passwords, payment fields and personal data.
12.3 Users can delete their account and data
Deletion actually removes their data from the database, file storage and connected tools.
13 Mobile app (Expo)
Only if the project has a mobile app. App bundles ship to users' phones, so anyone can open them up.
13.1 Tokens are stored securely
Login tokens use expo-secure-store (iOS Keychain, Android Keystore), never AsyncStorage or plain files.
13.2 No unencrypted traffic
All calls use HTTPS. Android doesn't allow cleartext traffic and iOS App Transport Security has no broad exceptions.
13.3 Deep links are safe
Links that open the app validate their parameters and never trigger payments, account changes or deletions without
login and confirmation.
13.4 In-app web pages are locked down
WebViews load only your own trusted URLs, and any bridge to the app exposes only what's needed.
13.5 Permissions are minimal
The app asks only for permissions it truly needs, when it needs them, with a clear reason.
13.6 Users can delete their account in the app
If users can create accounts, they can delete them inside the app. Both the App Store and Google Play require this.
13.7 The release build is clean
Debug menus, test screens, verbose logs and test endpoints are off in the store build. Push notifications never contain
codes or private data.
